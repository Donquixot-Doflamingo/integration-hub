## What was built
- **Admin server** (HUB-200/201): `internal/control/adminapi` — route table keyed by operationId, OIDC ES256 verification (JWKS via discovery) or the dev issuer stub (`HUB_ADMIN_DEV_OIDC`), RBAC per operation, AdminError envelope, `/me`, change log list/get, control-error mapping (404, 409, 412, 422 with the validation report, `RETIRE_BLOCKED` with counts). `Publisher.Edit` (validated config-tree edits under a Postgres advisory lock) and `control.WithChangeMeta`.
- **Vendors, capabilities, transformers** (HUB-202): CRUD with ETag/If-Match; immutable additive capability minors; transformer versions gated by their goldens; `dry-run` (credentials masked) and `run-goldens` with diffs.
- **Accounts, tenants, API keys, registrar** (HUB-203/206): write-only secrets, credential rotation and test-connection, lifecycle with the retire guard, keys shown once with rotation overlap enforced at the edge, registrar endpoints behind the SSRF guard and `HUB_CALLBACK_HOSTS`, signing-secret rotation with overlap; disabled endpoints get no callbacks.
- **Integrations and snapshots** (HUB-204/205): reads, structured + unified diff, drafts in Postgres, validate, publish / rollback / weights with `expected_active_version`, If-Match on metadata, snapshot list/get/blob and the `latest` long-poll.
- **Requests, sealing, DLQ, breakers** (HUB-207/208/209): indexed cursor search, timeline and attempts, `sealed` payloads (per-tenant AES-GCM, HKDF from the dev key) with audited unseal, DLQ list/replay/purge by ids or filter, breaker board and force-open/close shared through Redis.
- **hubctl** (HUB-210/211/212): `login -dev`, `whoami`, `export`, `plan`, `apply`, `dry-run`, `replay`.

## How it was built
The foundation (HUB-200/201) was written first; four agents then built the resource groups in parallel worktrees with their own Postgres and Redis, and their branches were merged here. Merge fixes: migrations renumbered to stay contiguous (00008 ops indexes, 00009 integration drafts), duplicate helpers kept once, one name clash renamed.

## Found and fixed
- **New accounts came back `draining`** (M6 publisher): every unreferenced active account drained on each commit. Draining now applies only to accounts that lost their last reference in that edit.
- **Concurrent publishes could start from the same base**: all config edits now hold a Postgres advisory lock from load to commit.
- **Reasons were only checked for non-blank**: the contract's 3–1024 characters are enforced.

## Deferred
- Console wiring to the real issuer and API (HUB-282, EP-10).
- `hubctl apply` for vendors, transformers, new accounts and new integrations (refused today with the endpoint to use).
- KMS-backed seal keys (`audit.SealKeys`); dev derives them from the local key file.
- An edge path for `no_active_version` (integrations created but never published answer `INTEGRATION_NOT_FOUND`).

## Deviations
1. **Admin-only metadata lives under `admin/` in the config tree** (vendor display names and revisions, capability minor records, transformer authorship): the registry's strict loader refuses unknown fields, so these sit beside the objects; hubctl treats `admin/` as server-owned.
2. **Capability schemas created through the API live in the snapshot archive**, not in the repo's `contracts/` (a new minor shadows the repo file inside the archive).
3. **Drafts and never-published integrations are Postgres rows**, not config files (nodes must not see them; the registry refuses an integration with no version). A draft's number is always latest + 1.
4. **Version metadata (published_at/by, based_on, copied_from) is read from change-log rows**; there is no metadata table.
5. **Vendor write operations answer 400 for publish-check failures** (the contract declares no 422 for them).
6. **test-connection writes an audit change row without a change_id** in the response (non-mutating per the contract, audited per DESIGN).
7. **Registrar delete is refused while any version subscribes**, not only active or draft ones (a non-active subscriber would break the snapshot build).
8. **Breaker fields the nodes do not share** (`failure_ratio`, `window_calls`, `consecutive_timeouts`) are reported as 0; `last_probe` is null.
9. **Timeline**: `request.dead_lettered` is shown as `request.failed`, `retry.scheduled` is omitted (not in the contract enum); payload-less events report the sha256 of zero bytes.
10. **`hubctl apply` applies a subset** (integration metadata, pause, new active versions, account config/quota, tenant settings) and refuses the rest before changing anything.
11. **Dev OIDC stub endpoints** (`/.well-known/openid-configuration`, `/oidc/*`) are outside `/admin/v1` and not in the contract: they are an identity-provider stand-in (DESIGN §19 M7), on only with `HUB_ADMIN_DEV_OIDC=true`.

## Contract change requests (for the contract-steward)
- `createVendor` example's `health_probe.endpoint` cannot be valid at create time; consider 422 on vendor writes.
- `TransformerVersion.vendor_endpoint` / `TransformerSummary.vendor_endpoint` nullable for response transformers; `GoldenFixture.expected_session`; drop or support `TransformerKind: inbound`; add `additive_change` to the documented checks.
- `DeliveryPolicy.polling: boolean`; `DiffOp.before/after` nullable; document `getLatestSnapshot` on an empty archive (304, ETag `"0"`).
- `TimelineEventType`: add `request.dead_lettered`, `retry.scheduled`; 404 vs 403 for out-of-scope `tenant_id` filters on lists; document node-local breaker counters.
- `createAccount` (state `active`, now true), `createRegistrarEndpoint` 404 for an unknown tenant (answers 400 today).
