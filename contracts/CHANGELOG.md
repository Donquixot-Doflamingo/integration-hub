# Contracts changelog

Contract versions, newest first. Each document has its own semver (see `README.md` § Versioning).
Entry format: `- YYYY-MM-DD · <document> <version> · <CCR / HUB-###> · <summary>`.

## 2026-11-07

- 2026-11-07 · `hub-admin` 2.0.0 · HUB-432 (ADR-0023) · Capabilities removed; operations and request schemas on integration versions, request schema on vendor endpoints (breaking, major; approved by the product owner 2026-11-07, pre-1.0)
  - Removed: `listCapabilities`, `createCapability`, `getCapability`, `listCapabilityVersions`, `createCapabilityVersion` (`/capabilities*`), the `capabilities` tag, parameter `CapabilityKey`, schemas `CapabilityKeyValue`, `CapabilityName`, `CapabilityOperationDef`, `CapabilityOperations`, `CapabilityCreate`, `CapabilityVersionCreate`, `CapabilityVersion`, `CapabilitySummary`, `CapabilityList`, `CapabilityVersionSummary`, `CapabilityVersionList`, `CapabilityVersionChange`; the `capability` field of `Integration`, `IntegrationSummary`, `IntegrationCreate`, `TransformerVersion`, `TransformerSummary`, `TransformerVersionCreate`, `TransformerDraft`, `RequestSummary`/`RequestDetail`; the `capability` query filter of `listIntegrations` and `listTransformers`; `capability` from `ObjectType`; check name `response_conforms`. 74 operations (was 79).
  - Integrations: `IntegrationCreate` and `Integration` gain `interactive` (boolean, default false, fixed at creation). `IntegrationSummary` gains `interactive` and `operations` (operation names of the active version).
  - Integration versions: `IntegrationSpec.operations` is required (new schemas `IntegrationOperations`, `IntegrationOperation`, `OperationRequestSchema`, `JsonSchemaDocument`): per operation name (`default` for one operation) `description`, `idempotent` (required), `validate_input` (default true; live calls get 400 `VALIDATION_FAILED` on mismatch) and `request_schema { body (required), headers }`, JSON Schema 2020-12 with `x-pii`. `TransformerPair.response` is optional and nullable (null = pass-through). `DeliveryPolicy.ttl_ms` omitted/null = Hub default.
  - Vendor endpoints: `request_schema` (`EndpointRequestSchema { path, query, headers, body }`, `{}` allowed) is required on `VendorEndpointCreate` and always returned on `VendorEndpoint`; optional informational `response_schema` (object or null). `AuthScheme` adds `none`. `AccountCreate.credentials` is optional (required unless the vendor's scheme is `none`; omitted or `{}` for `none`). `Credentials` loses `minProperties` (kept on `CredentialAddNext`).
  - Transformers: `vendor_endpoint` is required for `kind: request` (and `inbound`), absent/null for `kind: response` (nullable in responses). Fixtures are documented as samples; `GoldenFixture.input_headers` added. `TransformerDryRunRequest.headers` is renamed `input_headers`. New `SchemaViolation`; `TransformerDryRunResult.schema_errors` and `GoldensRunResult.results[].schema_errors` added. `createTransformerVersion` documents the sample checks `goldens_pass` and new `endpoint_schema` and gets its own 422 examples.
  - Validation: new check names `input_schema` and `endpoint_schema`; `ValidationCheck` and `AdminError.details[]` gain `sample` and `field` (JSON pointer of the offending field). `validateIntegrationVersion` documents `schemas_compile` (operation schemas and `req.*`/`hdr.*` references), `input_schema`, `goldens_pass`, `endpoint_schema`, `operations_have_transformers`, `interactive_sync_only`.
  - Examples: every spec example carries `operations`; new examples for an auth `none` vendor and account, a GET endpoint with a query schema, request/response transformers with samples, a pass-through draft, failing goldens and endpoint-schema 422s.
- 2026-11-07 · `hub-public` 2.0.0 · HUB-432 (ADR-0023) · Discovery returns operations with request schemas; pass-through responses (breaking, major; approved by the product owner 2026-11-07, pre-1.0)
  - Removed: `getCapability` (`GET /v1/capabilities/{capability}`), `CapabilityNotFound` response, error code `CAPABILITY_NOT_FOUND` (`schemas/events/canonical-error.json`), schemas `CapabilityKey`, `CapabilityOperation`, `CapabilityDescriptor`; the `capability` filter of `listIntegrations`; `capability` on `IntegrationSummary` and `RequestStatus`; `capability_url` on `IntegrationDetail`. 14 operations (was 15).
  - `IntegrationSummary.operations` is now `OperationDescriptor[]` (`name`, `description`, `idempotent`, `request_schema { body, headers? }`); empty while there is no active version.
  - Pass-through: new header `X-Hub-Pass-Through: true`, new response `PassThrough` used as the `default` response of `invokeIntegration` and `invokeIntegrationOperation`, new schema `RawBody` (`*/*`). `InvokeOk` adds a `*/*` media type and the `X-Hub-Pass-Through` and `Retry-After` headers. `CanonicalResponse` is any JSON value (was object); `RequestStatus.result` follows, and `request.completed` `data.result` is any JSON value.
  - Descriptions: `VALIDATION_FAILED` only when the operation has `validate_input` on; caller headers declared in `request_schema.headers` are the only ones the transformer sees (`hdr.*`); envelope `operation` and canonical-error `details` reworded. Examples renamed (`track_event`, `age_estimate`) and a pass-through example added. D12 unchanged apart from the existing dry-run exception.
- 2026-11-07 · `hubmcp-tools` 2.0.0 · HUB-432 (ADR-0023) · Tools mirror the capability removal (breaking, major)
  - Removed tool `hub_admin_list_capabilities`; `hub_describe_integration` maps to `getIntegration` only and returns `{ integration }`; the `capability` input/output fields of `hub_list_integrations`, `hub_get_request`, `hub_admin_list_integrations`, `hub_admin_get_integration`, `hub_admin_create_integration`, `hub_admin_get_transformer`, `hub_admin_create_transformer_version` and the transformer drafts; 4 capability entries of `not_exposed_operations`. 41 tools (5 tenant, 20 admin read, 16 admin write).
  - Discovery outputs carry `operations[]` with `request_schema`; `hub_invoke` and `hub_dry_run` take optional caller `headers` (only names declared in `request_schema.headers`); `hub_invoke` output gains `pass_through` and `result` is any JSON value.
  - Admin tools take the new fields: `hub_admin_create_vendor_endpoint` requires `request_schema` (+ optional `response_schema`), vendor `auth_scheme` adds `none`, `hub_admin_create_integration` takes `interactive`, transformer tools take `input_headers` and optional `vendor_endpoint`, goldens/dry-run outputs carry `schema_errors`, draft `spec` descriptions list `operations`.
  - `forbidden_operations` unchanged (still no tool maps to a DELETE or a forbidden operation; `createAccount` stays forbidden because its body carries credentials).
  - Tooling: `contracts/schemas/capabilities/` deleted; `tools/check.mjs` no longer registers the `interactive`/`operations` keywords, `tools/version-check.mjs` no longer treats that folder as a document kind; README documents the in-place major bump and the `x-pii` catalogue.

- 2026-11-07 · `hubmcp-tools` 1.1.0 · HUB-314 · Admin write tools acting as the signed-in user, with no delete path (additive, minor)
  - 34 new `hub_admin_*` tools, each mapped to exactly one existing hub-admin operation. 18 are read tools or non-mutating checks: list/get tenants, vendors, vendor endpoints and accounts, list capabilities, get transformer, run goldens, transformer dry-run, list/get integrations, get version, diff versions, validate, get registrar endpoint. 16 are write tools: create/update tenant, create API key, create/update vendor, create vendor endpoint version, update account (config and quota), create transformer version, create integration, create/update draft, publish, set weights, rollback, create/update registrar endpoint. 42 tools in total. No new HTTP endpoint.
  - Write tools use the user's own `HUB_ADMIN_TOKEN`, are registered only on stdio, and require `reason` (3–1000 characters; hubmcp appends ` (via hubmcp)`). The Hub's `x-required-role` is the authority (`FORBIDDEN` comes back as an `isError` result).
  - New per-tool fields: `maps_to[].http_method` (on every tool), `requires.transport: ["stdio"]` on write tools, `requires_confirm` (`live_traffic`: publish, weights, rollback and the four updates; `mints_secret`: API key, callback endpoint), `sensitive_output` (`/secret`, `/signing_secret`). Get tools return the `etag`, and update tools take `if_match`.
  - New top-level fields: `forbidden_operations` (17: the DELETE, purge, replay, unseal, account lifecycle, `createAccount` (body requires credentials), the three credential operations, the three breaker-force operations, pause/resume, API-key revoke/rotate, signing-secret rotation), `not_exposed_operations` (24; every one of the 79 hub-admin operations is classified exactly once), `forbidden_input_properties` (secret names), `forbidden_mutation_input_properties` (`disabled`, `paused`, `state`), `secret_patterns` (hubmcp refuses arguments carrying a Hub key or signing secret: new MCP-only code `SECRET_IN_INPUT`).
  - `rules`, `server.description` and the `HUB_ADMIN_TOKEN` description are rewritten for write tools. Existing tools are unchanged apart from `http_method`. `contracts/tools/check.mjs` §7b enforces all of the above. `hub-public` and `hub-admin` are unchanged.
- 2026-11-07 · `hub-admin` 1.2.0 · HUB-344 · Per-operation transformer pairs on integration version targets (additive, minor)
  - New schema `TransformerPair` (`request`, `response`: `TransformerRef`, both required). `TargetRef.transformer` now references it; its shape is unchanged and it stays required, as the default pair.
  - New optional `TargetRef.operations`: map from operation name (`OperationName`) to `TransformerPair`, at least one entry. A listed operation uses its own pair; others use `transformer`. Applies to `targets[]`, `failover[]` and `shadow.target`, so `IntegrationSpec` in drafts, versions, validate, publish, diff and `Integration.active` carries it.
  - `ValidationCheck.check` names the new known check `operations_have_transformers` (unknown operation key, or a pair compiled for another operation); clients must tolerate unknown check names.
  - Examples: `createIntegrationDraft` request and `getIntegrationVersion` 200 move from `example` to named `examples` (the existing one stays first) and add `per_operation` for `kyc.aadhaar_otp@v1` (`generate` default, `verify` override).
  - `hub-public` unchanged: callers never see transformers. `hubmcp-tools` unchanged: no tool exposes the target shape.

## 2026-10-31

- 2026-10-31 · `hub-admin` 1.1.0 · CCR-003 / HUB-284 · Per-account dead-letter count and age on `AccountSummary` and `Account` (additive, minor; extends the pending 1.1.0)
  - New optional response properties `dead_letter_count` (integer ≥ 0) and `dead_letter_oldest_at` (date-time or null): dead letters whose last attempt used the account, not replayed, within the 14-day retention; may lag by up to a minute.
  - Returned by `listAccounts` (`AccountSummary`) and `getAccount` (`Account`). Examples updated: `ct-brandA-in` has 1 (matching the `listDeadLetters` example), a second list row shows 0 and null.
- 2026-10-31 · `hub-admin` 1.1.0 · CCR-002 / HUB-283 · Active-version filters on `listIntegrations` (additive, minor; extends the pending 1.1.0)
  - New optional boolean query parameters `has_active_version` (published or never published) and `active_version_behind` (a newer version or a draft waits behind the active one), with examples. `VALIDATION_FAILED` for a non-boolean value, as for `paused`.
  - The operation description says filters combine with AND and apply before pagination.
- 2026-10-31 · `hub-admin` 1.1.0 · CCR-001 / HUB-278 · Every admin response declares `X-Hub-Request-Id` (additive, minor)
  - New `components.headers.X-Hub-Request-Id` (`req_` + ULID, required, equals `error.request_id` on errors), referenced by all 80 inline responses of the 79 operations and by the 9 shared `components.responses`.
  - `info.description` documents the header. No body, parameter or schema change.
  - 1.1.0 is the pending version of contract round 1: HUB-283 and HUB-284 extend it in the same release.
- 2026-10-31 · `hub-public` 1.0.1 · HUB-033 · `getReadyz` 503 example matches what `/readyz` returns (patch, example and description only)
  - The example has one `details` entry with `message` only (`redis unreachable`), as the backend emits it; the old entry carried a `pointer` into a request body that `/readyz` does not have.
  - The example drops the `circuit`/`reason`/`upstream` nulls the backend omits, and keeps its `request_id` (already present in 1.0.0; the CCR's "before" snippet predates the freeze).
  - The description says each entry names one failing check and that `request_id` equals `X-Hub-Request-Id`. No schema change.
