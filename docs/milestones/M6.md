## What was built
- **Publisher** (HUB-170/172/176): `control.Publisher` edits the archived config tree (comments kept), runs the full `registry.Build` including goldens, archives the snapshot, writes a `hub.change_log` row and pings `hub:snapshot`. Rollback = new version with the old spec. Accounts drain automatically when no active version targets them; `RetireGuard` counts pinned/session envelopes and open sessions.
- **Change log** (migration 00007): append-only (trigger), actor, roles, reason, before/after, snapshot version.
- **Distribution** (HUB-171): every node subscribes to `hub:snapshot` and polls the archive every 5 s; builds in the background, swaps atomically, keeps the last good snapshot.
- **Send-time version** (HUB-174): worker re-resolves unless pinned or session-bound; every attempt records its version.
- **Vendor sessions** (HUB-175/183, sessions worktree): `session:` section in response transformers, `hub.vendor_sessions` (migration 00006, Aadhaar-like numbers refused by CHECK), `X-Hub-Session` pinning in the edge and worker, scheduler sweep every 30 s.
- **Credential rotation** (HUB-177): `active` / `next` / `previous` slots, `control.Rotator` (add next → promote → delete old, optimistic expected versions), `hub:creds` ping reloads every node's cache, each decrypt logged without values.
- **Shadow** (HUB-173): `shadow: {target, mode, sample_ratio}` on a version; `delivery.Shadower` copies after the caller's answer (64 in flight, 5 s each), own audit block, `shadow_total`.
- **Per-version goldens** (HUB-341): `fixtures/v<N>/` when a version changes its output.
- **Cutover fixtures** (HUB-178): test overlay with a second account, a test-only second vendor (`altvendor`) and `T1@8`.

## Found while building and fixed
- **Shared goldens blocked new transformer versions** (design gap): a T1@8 with different output could not pass T1's fixtures without breaking T1@7. HUB-341 adds per-version fixture folders.
- **sqlc models were not regenerated for migration 00007**: `make sqlc-check` would have failed CI; fixed before the PR.
- **ADR number clash**: both worktrees wrote an ADR-0010; the session one is ADR-0011.
- **Shadow vs sessions**: a session step ≥ 2 is never shadowed (the shadow target has no such vendor session).

## Deviations
1. **Nodes follow the archive (Redis ping + 5 s poll), not a long poll of `/admin/v1/snapshots/latest`** — [ADR-0010](../tech/adr/0010-registry-source-of-truth-is-the-snapshot-archive.md).
2. **Session step ≥ 2 does one primary-key read on Postgres on the sync path** (§18.5 says no DB reads) — [ADR-0011](../tech/adr/0011-vendor-session-lookup-on-the-request-path.md). Requests without `X-Hub-Session` never touch the DB.
3. **Shadow copies are audit events only**: no `request_attempts` rows (the attempt key and the `served_by` column do not exist yet); the block starts with `integration.resolved` meta `served_by: shadow`. No new timeline event types were added.
4. **"Side-effect vendor" = non-idempotent vendor endpoint**: the registry has no other side-effect marker; `send` shadows to such endpoints are refused at publish.
5. **Credential fingerprint identifies the write, not the ciphertext**: the local file has no per-slot ciphertext to hash.
6. **The change-log row is written before the credential store**: a failed store write leaves an entry for a change that did not land (the error names it), rather than a change without an entry.
7. **Session step ≥ 2 has no failover**, and orphan sessions from late wait-mode step 1s simply expire (see ADR-0011).
