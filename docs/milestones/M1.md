## What was built
- **Types** (HUB-040): every registry object. The DESIGN §3.4 and §8.3 examples round-trip verbatim.
- **Loaders** (HUB-041/042):
  - Strict YAML (unknown fields fail), ids must equal file names.
  - Capability schemas are compiled once from `contracts/` (JSON Schema 2020-12) with `operations`, `interactive` and `x-pii` paths.
  - API keys are stored as hashes only.
  - D3/D4/D10 delivery defaults are applied.
- **Validation** (HUB-043): references, weights, interactive ⇒ sync, polling or webhook for non-sync modes, failover chains, registrar ownership, retired accounts. Every problem is reported in one pass as `file: path: message`.
- **Snapshots** (HUB-044): `registry.Build`, plus a sha256 checksum over the sources and an atomic-pointer `Store` with strictly increasing versions.
- **Dev watcher** (HUB-045): opt-in (`-config-watch`). It swaps in about 1 s and keeps the last good snapshot on invalid edits. All roles load a snapshot at start; `/readyz` has a `snapshot` check (M0 deviation 6 closed); metrics are `snapshot_version` and `snapshot_apply_failures_total{reason}`.
- **Dev config** (HUB-046): `backend/config`, with a documented test-only dev API key.
- **Registry tables** (HUB-047): 13 tables, triggers that reject `UPDATE` on versions and transformers, sqlc 1.31.1, and a CI `sqlc` freshness job.
- **Persistence** (HUB-048):
  - The admin role archives snapshots (`hub.config_snapshots` plus a blob of the sources, checksum-verified on load).
  - Data-plane roles boot from the archive, then from a local cache, when their config cannot be built.
  - The scheduler prunes snapshots after 90 days, always keeping the newest.

Coverage (unit): `internal/registry` 82 %, `cmd/hub/internal/roles` 85 %. `internal/control` is covered by integration tests that drive it through the roles package (Go reports those as 0 % for the package itself).
