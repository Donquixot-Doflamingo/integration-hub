# Backend skills

Skills Claude Code loads automatically when working under `backend/`. Each folder holds a `SKILL.md` (frontmatter `name` + `description` decide when it triggers) and optional `references/` for longer material. Repo-wide skills (PRD, tickets, ADRs, skill-creator) live in the root `.claude/skills/`.

| Skill | Purpose | Triggers when you… |
| --- | --- | --- |
| [`go-idioms`](go-idioms/SKILL.md) | Effective Go for this repo: naming, errors + canonical codes (§4.4), context, consumer interfaces, options, immutable snapshots / `atomic.Pointer`, no globals, lint config | write, refactor or review any Go code |
| [`go-architecture`](go-architecture/SKILL.md) | Package layers and allowed imports (§18.1/§18.3), ports/adapters, where new code goes, config loading, constructor DI, shutdown order | add a package/file/import, wire `cmd/*`, add a role, vendor, auth scheme or middleware |
| [`go-system-design`](go-system-design/SKILL.md) | Outbox + SKIP LOCKED, at-least-once + idempotency, CAS transitions, jittered retries + budget, shared breaker, token buckets, bulkheads, backpressure, TTL, drain ramp, leader election, snapshot distribution, cutover — with failure tables | work on queue, delivery, upstream, scheduler, registry distribution or resilience |
| [`go-testing`](go-testing/SKILL.md) | Table tests, `-race`, `t.Parallel`, goldens with `-update`, integration tags + testcontainers, mockvendor, kin-openapi contract tests, fuzz, p99 benchmarks, goleak, synctest, chaos tests, make targets | write or fix tests, benchmarks, fuzzers, or prove an acceptance criterion |
| [`go-memory-performance`](go-memory-performance/SKILL.md) | pprof on the internal port, benchmem/profiles, escape analysis, `sync.Pool`, hot-path allocations, GOMEMLIMIT, runtime/metrics, goroutine leaks, benchstat gating, traces, leak runbook | see memory/goroutine growth or a latency regression, or touch the sync path |
| [`go-logging`](go-logging/SKILL.md) | slog JSON schema, redact-by-value handler, level policy, no bodies, log once at the boundary, sampling, trace correlation, no-secret tests | add or change log lines or loggers, handle errors at a boundary, touch credentials |
| [`go-debugging`](go-debugging/SKILL.md) | Reproduce with mockvendor, Delve, race output, goroutine dumps, GODEBUG/GOTRACEBACK, httptrace, audit timeline, Postgres/Redis debugging, Hub failure signatures | chase a failing/flaky test, hang, race, wrong canonical code, stuck outbox rows |
| [`go-observability`](go-observability/SKILL.md) | OTel metrics + traces, naming/units, ms buckets, cardinality, per-middleware durations, `hub_overhead_ms` breakdown, span names, traceparent, exemplars, alerts and dashboards as code | add a metric, span, middleware, alert or dashboard |
| [`postgres-patterns`](postgres-patterns/SKILL.md) | pgx pools, sqlc, goose, day partitions, outbox indexes, SKIP LOCKED claim, CAS updates, advisory locks, isolation, JSONB, migration tests | write SQL, migrations, sqlc queries or Postgres adapters |
| [`hub-transformers`](hub-transformers/SKILL.md) | Transformer YAML DSL (§7), context vars, stdlib, `creds.*` rules, error mapping, batch, golden fixtures, vendor-doc citation, `hubctl transform test`, config over fork | add/change a vendor mapping or goldens, debug `TRANSFORM_FAILED` |
| [`api-contract-backend`](api-contract-backend/SKILL.md) | Contract-first handlers: change requests to contract-steward, operationId mapping, error envelope helper, kin-openapi validation, no vendor identity, versioning | add or change a handler, route, response shape, header, error code or event |
| [`mcp-builder`](mcp-builder/SKILL.md) (vendored, third-party) | General guidance for designing MCP servers and tools, with evaluation tooling | build or change `cmd/hubmcp` tools. Its code examples are TypeScript/Python; our server uses the official Go SDK (`github.com/modelcontextprotocol/go-sdk`) and talks to the Hub only through the contracted API (`go-architecture`) |

Conventions for adding a skill here: kebab-case folder = `name`, a pushy "Use when…" description, `SKILL.md` under ~250 lines with details in `references/`, repo-specific rules over generic advice, no invented library APIs. Third-party skills keep their `LICENSE.txt` and are listed in the root `THIRD_PARTY_SKILLS.md`.
